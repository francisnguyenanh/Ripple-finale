# Final knowledge loop — operator recovery steps (supported environment: one PostgreSQL, one blob store, one or more workers)

Every durable write of the loop is one transaction under the workspace row lock with CAS on the head, an idempotency ledger and an outbox event; workers run under
leases with fencing tokens. Recovery therefore never rewrites history: it retries, re-queues or re-reads. Nothing below needs a model call or spends budget.

| Symptom | What it means | Recovery |
|---|---|---|
| `GET /v2/business/knowledge` shows `index.pending_events > 0` for a long time | the `BUSINESS_KNOWLEDGE_COMMITTED` event of an accepted snapshot has not been consumed (no worker, or the index build keeps failing) | start/inspect a worker for the workspace; a failing build is retried per claim and ends as a failed outbox row after five claims (`v2_outbox.status`); fix the cause, then re-queue by resetting that row's status to `PENDING` (its payload names the snapshot; `build_index` is idempotent) |
| A knowledge commit returned an error and the head did not move | the transaction rolled back (CAS, authority, stale pin) | nothing to repair; the caller repeats with the current binding/head |
| A `document.generate` job is `FAILED` | the request hit a ceiling (rules/size) or the snapshot is unavailable; no bytes were written | read `execution_reason`; the artifact id is the job id, so the same request stays failed by design: change the request (scope) or raise the operator ceiling, then request again |
| A document row exists but `GET .../content` answers 409 `integrity` | the blob is missing or corrupt (store incident) | restore the blob store from its backup; documents are deterministic, so a lost blob can be regenerated by deleting nothing: request the same key with the row removed by a DBA under the immutability trigger disabled, or treat the version as unavailable |
| Blobs without a row after a crash during generation | staging happened, the row insert did not | harmless (content-addressed); the next identical request regenerates deterministically and writes the row once |
| `business.source_apply` job `FAILED` with `approver_authority_revoked`, `stale_current_value`, `source_moved`, `ambiguous_key`, `edit_not_isolated` | the guards refused before publishing; nothing was written | a person edits the files by hand (manual path) and refreshes the sources, or re-approves after the sources are reviewed again; a new approval produces a new job id |
| `business.source_apply` job `FAILED` with `readback_failed` | the revision WAS published; its observations were not recorded | run `POST /v2/business/analyse` (the carry-over reports `unverifiable`/`mapping_lost` honestly); re-record observations by a source refresh of the same files, which re-ingests them |
| Worker log shows `LeaseLost` | another worker took over an expired lease; the fenced worker wrote nothing | nothing to repair; check the lease seconds against the slowest job |
| A QUEUED job never runs | no worker for that workspace, the AI switch is off (AI kinds stay queued by design), or the per-job budget admission cancelled it (`budget_exceeded`) | start a worker / turn the switch on inside an approved window / read the cancel reason; deterministic kinds (`document.generate`, `business.source_apply`, `source_ingest`) run with the AI switch off |
| Stale documents after a knowledge change | expected: artifacts are per knowledge version | nothing to repair; a person opens the topic again (explicit generation for the current version) |
| `GET /v2/projection/status` shows a growing lag | no projector pass ran, or the sink is unavailable (every pass raised and the checkpoint did not move) | run `POST /v2/projection/run` (`membership.manage`) once the sink is back; the replay is idempotent (same keys, higher revisions ignored by the sink); clients keep bounded polling meanwhile |
| A notification delivery stays `PENDING` or `FAILED` | the transport failed up to 3 times | the inbox item exists regardless (the full path); a later `POST /v2/notifications/dispatch` retries pending deliveries only; a FAILED delivery is not retried (new intent needed) |
| An external sign-in answers 401 for a known person | the subject is not linked, the link was revoked, the token is for another project/tenant, expired or older than the freshness window, or the account is disabled | read the `external_identity.denied` audit row (reason code only); link or re-link the subject with `POST /v2/auth/external/links`; the person signs in again at the provider |
| `GET /v2/business/mining` shows a group `failed` | that group's `knowledge.mining` job failed (`reason` names it: model answer unusable, knowledge or group moved, config moved) | the other groups still count in the coverage; request mining again with the next `attempt` (1-3) on the current version; nothing was written |
| A coder/tester run ends `INCOMPLETE needs_human:…` | the repair loop stopped (cap, nothing proposed, candidate failed, no progress) | read `report.tests.history` and `report.tests.repairs`; a person fixes the code or widens the mapping; a new candidate starts a new run (attempts are never reset inside a run) |
| An interview shows `question_pending` for a long time | the `gap.interview_question` job has not run or failed | a worker completes it; a failed job settles into the deterministic question automatically on the next refresh; the controls work meanwhile |
| A document variant stays `generating` | its `document.variant` job has not run (no worker, pending approval) or failed | `GET /v2/business/documents/variants/{id}` shows `failure_reason`; a `config_moved` or `base_unavailable` failure needs a new request on the current base; the base document itself is unaffected |
| An interview session (`GET /v2/business/interviews/{id}`) shows a turn with a `job_id` and no reading for a long time | the KNO-07 reading job of that turn has not run (no worker, pending approval, or failed) | inspect the job (`GET /v2/jobs/{job_id}`); a worker completes it and the next `GET`/`refresh` pulls the reading in; a `FAILED` job shows as a FAILED reading and the question is asked again; the structured controls work at any time |
| A multi-agent run stays `RUNNING` although every child is terminal | a worker died between a child's completion and the creation of its join job | `POST /v2/ma/runs/{run_id}/advance` (idempotent; `ma.run`): it syncs the children, dispatches planned ones, runs the rebuttal round or finalizes; a run past its deadline ends `INCOMPLETE` with pending children cancelled; `cancel` releases the root reservation |
| Upgrade of a populated database | the migration chain is idempotent and additive | run the service once; verified by `tests/final_loop/test_rel02_upgrade_chain.py` (every row byte-identical, triggers intact) |

Not supported by this runbook: multi-region stores, point-in-time restore of the knowledge tables (restore the whole database; history is append-only), and any recovery that would rewrite a decision, a snapshot or a revision.
