# Request task view and request assistant — contract `ripple-request-task/1` (RUX-00 freeze, 2026-10-19)

Status: frozen for the first slices (RUX-01 task projection, RQA-01 visibility and context). Later slices extend this file; a change to a frozen field is a new version.
Nothing here grants a permission or changes a workflow: the task view is a read-only projection of the existing workflows, and the assistant is read-only.

## 1. Request families and locators
Two request families exist; their state machines stay separate and are never merged.

| Family | Locator `id` | What it is | Existing state source |
|---|---|---|---|
| `intent_flow` | `intent-…` (canonical once an intent exists) or `chat-…` (a change-request conversation before its intent) | free-text change request -> intent -> draft -> impact / simulation -> proposal -> review -> approval -> apply -> verification -> result decision (Changes page) | `v2_chat_conversations`, `v2_intents`, jobs `change.draft`, `proposal`, `review`, `approval`, `apply`, review notes, verification contracts (`infra/v2_work_routes.py::_chain/_stage`) |
| `business_change` | `chg-…` (the `change.understand` job id) | confirmed change of the accepted business knowledge -> draft -> knowledge decision -> commit -> file-write decision -> source apply (Questions page, change review) | `infra/adapters/v2_business_review.py::review_view` (decisions, `what_actor_can`, commit, source, completion) |

The server resolves tenant, workspace and the current actor from the session and the validated workspace; a client never sends actor, roles or grants. A `chat-…` locator
whose conversation has an intent resolves to that intent (`canonical_ref`); lineage comes from stored bindings (conversation.intent_id, proposal payload `intent_id`, the
newest proposal of an intent replaces older ones through `previous_proposal_job_id`), never from a client list of job ids.

## 2. Read rules (reused, not new)
| Family / part | Who may read | Source |
|---|---|---|
| `intent_flow` conversation before its intent | its creator, or a holder of `knowledge.confirm` | `v2_chat_routes._visible` (unchanged; the assistant does not widen it) |
| `intent_flow` intent and its jobs | any member with `project.read` | job and intent routes |
| `business_change` | the person who asked, holders of `knowledge.confirm` or `change.approve` | `v2_business_routes._change_record_for` |
Anyone else gets the generic "request not found" (404), the same answer as for a request that does not exist. The generic job read (`GET /v2/jobs/{id}`) must not reveal a
`business_change` record or a job bound to one (`change_id` in its payload) to someone who may not read that change (RQA-01 closes this gap; before it the job route returned
such records to every `project.read` member). The workspace audit (`GET /v2/audit/{ws}`) applies the same rule (SCN-12, 2026-10-26): an event bound to a business change (its `chg-…` job, intent or change id, or a job whose payload names that change as `change_id` or `intent_id`) is returned only to the person who asked and to holders of `knowledge.confirm` / `change.approve`, and an event of a `request.qa` job only to the person who asked it; an unresolvable binding is withheld.

## 3. Task view (read-only) — `GET /v2/requests/{family}/{id}/task-view?workspace_id=`
```
{schema: "ripple-request-task/1", request_ref {family, id, canonical_ref?}, title, as_of, availability: available|partial|unavailable,
 stage {code, label, family_state}, obligations[], waiting_on[], blockers[], input_refs[], expected_deliverables[], permitted_actions[], stages[], completion_axes{}, coverage{}}
```
- `obligations[]`: `{code, label, required: bool, holder: you|role_pool|requester|system|unassigned|unknown, holder_label, eligible_me: bool, assigned_me: bool,
  state: current|waiting|blocked|future|done, reason?}`. `assigned_me` is true only where the workflow binds the obligation to this account (the requester of their own
  request); a permission alone gives `eligible_me`, never `assigned_me`. An administrator who is not a `change_approver` is not asked to decide (eligible, not obligated),
  the same rule as the inbox. A reviewer's review is `required: false` unless the workflow requires it. `label` names the step to do (e.g. "Ask for the AI draft of the
  change"), never the stage; `step` is the canonical step it belongs to (absent when it cannot be placed). The unblock path is the real one: after `request_changes` the
  requester holds `respond_to_changes` and the decision is `waiting` (the approver may still decide but is not asked); when the knowledge moved, `restate_request` (a new
  change request) is the only way forward and the dependent steps are `blocked` with nobody waited on; a committed change is not "moved" by its own commit.
- `waiting_on[]`: `{holder, holder_label, code, step?}`; the system is named as the system, never as "someone". No person's name, deadline or SLA is invented.
- `blockers[]`: `{code, text, source}` from the workflow (open "request changes" notes, semantic blockers, knowledge moved, failed jobs) and from the server (`ai_kind_not_enabled`, 2026-10-27: the role allowlist of this server does not enable the AI kind a step needs, e.g. `change.draft` for the intent-flow draft; that step is then asked of nobody and its reason says so; DEC-0009 / D2a: the screen names the equivalent enabled step, the business-change flow whose review asks for the dependency check and the guidance); never hidden behind a toggle.
- `permitted_actions[]`: `{action, label, allowed: bool, current: bool, reason?}` from the same predicates the action routes recheck; the task view never performs an action.
  `current` = allowed AND serving an obligation the reader is asked to do now; only current actions are offered as next steps (the assistant's `next_actions`, the page's
  next step). A permitted action is never a recommended obligation by itself. Labels are business words, not identifiers.
- `expected_deliverables[]`: `{code, label, later?}`: what the CURRENT step hands over (a decision is not a commit, a commit is not a file decision or a source sync);
  outcomes of later steps are marked `later: true` and shown apart.
- The route adds `features: {request_assistant: on|off}` (the page hides the launcher; the assistant routes refuse by themselves).
- `stages[]`: the family's canonical steps `{code, label, state: done|current|waiting|blocked|failed|future|not_applicable, parallel_group?}` in order; steps done by different
  people in either order share a `parallel_group` (business change: knowledge commit and file decision, `after_knowledge_decision`).
- `stages[].phase` / `phase_label` (2026-10-21): where the step stands, derived from what the record holds for it, never from the word `current`:
  - `running` = a system wait or an unfinished job on the step ("in progress");
  - `not_started` = the current obligation starts the step's work (ask for the draft, run the analysis / review, prepare the approval, apply, state a new request);
  - `awaiting_decision` = the current obligation is a decision; `awaiting_action` = another current obligation (confirm, answer, respond, commit);
  - `awaiting_other_step` = the step waits until another step is done; `blocked`, `failed` (failed or stopped), `done`, `future`, `not_applicable` follow the state;
  - `unknown` = a current step with no recorded wait, obligation or running work, shown as such.
  The task frame shows this phase (a spinning "in progress" badge only for `running`); the request assistant's context states the same phases.
- Work list `GET /v2/work/inbox` (RUX-04) places every readable request of both families by this projection only: `sections` = `mine` (a current required obligation the
  reader is asked to do), `optional`, `blocked` (the reader's request that nobody can move on its current path), `waiting_human`, `waiting_system`, `recent`; each item
  carries `family`, `page`, `params`, `stage`, `step`, `blocked`, `blockers`; a request whose view fails is counted in `unavailable`, never shown as "no work". The legacy
  `todo` / `waiting` / `recent` lists keep their meaning.
  - `coverage` (SCN-12, 2026-10-26, additive): `{scope: "loaded", candidate_limits{source: n}, truncated[source], recent_loaded, recent_shown, complete}`. The list is
    built from newest-first candidate sources, each read up to its limit: `proposal` and `business_change` (40 each); for a reader with `intent.create` also its own
    `change_request_conversation` (10) and `own_intent` (40). A source with more candidates than its limit is named in `truncated` (the sections may then miss requests;
    no total is computed). A reader without `knowledge.confirm` / `change.approve` reads only their own business changes as candidates, so the cut and `truncated` never reflect requests they may not read. `sections.recent` / `recent` show at most 5 of `recent_loaded`. `complete` is true only when `truncated` is empty and `unavailable` is 0.
    Section lengths are counts of request entries in this loaded list, not workspace totals; unreadable requests are excluded before anything is counted and never hinted.
    No server pagination, sort, filter or cursor exists; a consumer that needs one is a separate dependency.
- `completion_axes`: separate axes (knowledge, file writes, source apply, verification, result decision) as the family has them; never one combined badge.
- Unknown or failed reads are `unknown` / `availability: partial`, never "no work". The read writes nothing, runs no job and calls no model.

## 4. Assistant capability (RQA-01 freeze; routes in RQA-02)
- New permission `request.assistant.ask`, granted to readable human role bundles for this feature only; it admits only the job kind `request.qa` and nothing else; `ai.use`
  does not admit `request.qa` by itself. `ai_suspended` removes `request.assistant.ask` as it removes `ai.use`.
- Threads are private to their creator per tenant / workspace / request; no role inherits another person's threads.
- The context of an answer is built only from what the asking person may read through section 2 and the field catalogue of RQA-01, before retrieval and prompt.

## 5. Assistant routes, storage and answers (RQA-02 / RQA-03)
**Status: routes, storage, admission and worker implemented and verified locally with a stub model transport (no live model; answer quality not measured). The browser panel is not yet verified.**
| Route | Rule |
|---|---|
| `POST /v2/requests/{family}/{id}/assistant/threads {workspace_id}` | `request.assistant.ask` + the request readable; creates a private thread; **no model call** |
| `POST /v2/requests/{family}/{id}/assistant/ask {workspace_id, question, idempotency_key}` | EUI-02 first question: creates the private thread AND admits the question as one idempotent action. The thread id is derived from the caller, the request and the key, so a lost response, a retry or a concurrent click with the same key returns the same thread and message (`replayed: true`; at most one job and one reservation); another question under the same key: 409 `idempotency_conflict`; question and key are validated before any row is written; a failed admission leaves the empty thread and the same key retries once. | `GET /v2/requests/{family}/{id}/assistant/threads` | the caller's own threads of that request only |

| `POST /v2/request-assistant/threads/{thread_id}/messages {workspace_id, question, idempotency_key, after_seq}` | explicit ask; idempotent per thread + key (another question under the same key: 409 `idempotency_conflict`); `after_seq` must be the last message number (another window asked first: 409 `sequence_conflict`); one admitted `request.qa` job |

Only impact and draft rule-change facts carry sources; any other fact gives `no_source_locator`, and the page's own section is shown instead. Each source has: path, locator, binding revision, state against the current sources (`current` / `changed_since` / `absent_now`), and for a YAML key the stored value at that key, read through the source blob seam (no excerpt when no blob store is configured; never a guess). R11: the response carries `cancel {message_id, outcome: cancelled | running | finished}` as the record shows it after the request; a pending message carries `phase: queued | running`; an unavailable / cancelled answer carries `reason_code` (`provider_timeout`, `attempt_limit`, `provider_failed`, `cancelled`, `not_answered`) and `reference` (the message id) |
Storage: `v2_request_threads`, `v2_request_messages` (migration `ext_t10_request_assistant.sql`): question, context manifest hash and the asker's authorization fingerprint
at ask time, job id, and the validated answer once published. v1 retention: threads live with the workspace; no user delete, no sharing, no export (owner may revise
before release). `request.qa` jobs are not readable, approvable, retriable or cancellable through the generic job routes, and cannot be created through `POST /v2/jobs`.

Worker (`request.qa`, pinned role `request.assistant`, `config/request_assistant.json`): immediately before the provider call it rechecks that the asker still holds
`request.assistant.ask` and may read the request, and that the context rebuilt now under the asker's rights has the same manifest hash (`context_changed` otherwise: no call,
the person asks again). Answer `{status: answered|partial|insufficient_context|out_of_scope|refused, blocks[{text, fact_refs, kind: fact|interpretation|suggestion}],
rejected[{index, kind, reason}], limitations[], next_actions[], as_of, manifest_hash}`; a block is kept only if every cited fact was offered, every number in it is in a
cited fact, a suggestion rests on an action / obligation / blocker fact and does not contradict a cited "not allowed for you", it does not claim the assistant acted, and the
text is plain; `next_actions` are the reader's allowed actions from the task view, computed by the server. An answer is shown only under the same authorization fingerprint
it was asked with (otherwise `withheld` until asked again) and is marked historical when the request's context moved since.

## 6. Answer integrity v2 (AIG-01 typed authority, AIG-02 bounded priority context)
**Status: contract frozen 2026-10-20 before implementation; English is the only supported answer locale.**

**Answer schema `request-assistant-answer/2`.** The model returns `outcome`, `answer_blocks` (free explanation: `fact | interpretation | suggestion`), `limitations` and
`authority_assertions[]` (at most 4): `{subject: self | holder, fact_ref, relation: holds | must | may | waiting_on | blocked, polarity: true | false, scope: current | later}`.
`fact_ref` names one offered fact of kind obligation, action, waiting or blocker; `subject: holder` means the holder that fact names (a role pool, the requester or the
system), never a person's name. There are no free role, account, action or URL strings.
- An assertion is kept only when it is true of the cited fact's typed values: `holds` = the obligation is the reader's (`self`) or the named holder's, in the stated scope
  (current / later); `must` = the reader's AND required; `may` = eligible (obligation) or allowed (action); `waiting_on` = a waiting fact's holder; `blocked` = the cited
  obligation is blocked or a blocker fact is cited. `polarity: false` asserts the negation and is checked the same way. Permitted is not current duty, eligible is not
  assigned, later is not now, optional is not required.
- The decisive authority sentence is RENDERED by the server from a kept assertion and the canonical fact (controlled English phrases), shown as a block of kind
  `authority` with that fact cited. The model cannot replace it with its own wording.
- Free blocks carry the model's explanation (why a request is blocked, which decisions and rules led here, what trade-off remains), with citations. A free block that
  itself claims who holds, must, may or is waited on, or that opens with a bare "Yes"/"No", is refused (`authority_in_free_text`, `unbound_affirmation`): authority goes
  through assertions only. The earlier lexical checks stay as defence in depth; they are not proof of correctness.
- `status`: `refused` when nothing survives, `partial` when something was refused. A refused or empty answer to an answerable question is not a useful answer.
- Result identity: `answer_schema`, `checks_version` (`request-assistant-checks/4`), `locale` (`en`), `context_version`, `config_sha256`. Stored answers are never edited.
  An answer stored under an older schema is shown with a note that it was checked by an earlier version, and its free blocks that make authority claims are withheld on
  read (no model call, no rewrite). A question queued before an upgrade is answered under the configuration current when it runs and records that identity.

**Context `request-assistant-context/2`.** After the read rules, every fact carries a `tier` and a stable `key` (its source identity: obligation code, decision id, rule
title, note id). Mandatory tier: request identity, stage, the reader's obligations / eligibility, waiting, blockers, allowed and denied actions, progress, completion axes.
Support tier: the confirmed request, rule changes, impact, current decisions. History tier: older decisions and reviewer notes.
- All mandatory facts are kept and must be complete: if they do not fit the fact count or one of them would be cut, the ask is refused with `409 context_overflow`
  (worker: `context_overflow` before any provider call). Nothing is dropped silently and no limit is raised.
- Support, then history facts fill the remaining room in a stable order (tier, kind, key), never by database enumeration or read time; optional facts that would be cut
  carry `truncated`. Structured values are never cut mid-object.
- `coverage` reports offered / selected / omitted per tier and upstream caps (for example the impact list limit), only from what the reader may read.
- Local ids `F1..Fn` are assigned on copies after ordering and belong to that stored pack; the manifest hash binds facts (with tier and key), coverage, context version and
  authorization, so two reads of the same frozen state give the same pack and a real change (a new blocker or decision, lost access) gives `context_changed`.

### 6.x Answer integrity v3 (AIG-03 v5: `request-assistant-answer/3`, `request-assistant-checks/5`, config version 3)
- **`cause` block:** a new block kind that says WHY the request is where it is, written about the request (never about who may, must or can act).
  - It must cite a fact with business substance (blocker, decision, rule change, impact, request, waiting, review note); otherwise it is refused as `cause_without_cause_fact`.
  - Authority in its prose is refused like any free block (`authority_in_free_text`). The whole block is refused; nothing is cut out of it.
- **Blocker coverage:** computed by the server for every answer, from the offered pack and for any request, with no expected ids: `blocker_coverage {offered, explained, unexplained}`.
  - An offered blocker that no kept explanation cites is disclosed as a limitation, "Not explained in this answer: …", using the blocker's own text. Nothing is made up for it, and the status is unchanged.
  - With no blocker offered, nothing is added.
- **Compatibility:** answers stored under `request-assistant-checks/4` are shown as stored (their authority is already typed and server-rendered). Older ones keep the legacy view. Nothing is regenerated.
- **Quality:** the prompt asks for every offered blocker to be explained or named in the limitations. Model compliance is measured only by a live cohort under its own approved allocation; the R1 / Q1 runs were made on answer/2 and stay as recorded.

### 6.y Corrected authority (`request-assistant-checks/6`; answer schema, prompt and config unchanged)
- A typed assertion the cited fact contradicts stays refused (`assertion_contradicts_fact`, counted in `rejected`). When the same fact decides the right answer to the question the model raised, the server shows that sentence instead, as an `authority` block with `corrected: true`. The UI marks it "corrected: the assistant's claim did not match the task record".
- What the fact decides:
  - a step held by someone else that the model gave to the reader (holds / must) → "This step is not yours" (true whatever the step's stage);
  - a claim about the step's own stage → its opposite;
  - a current claim about a blocked step → "This step is blocked";
  - a current claim about a later step → the same claim for later.
  Every candidate is re-checked against the fact before it is shown. Nothing is corrected from a finished step, an unsupported combination or an unknown fact. A sentence already shown is not repeated.
- Authority stays deterministic: the model only chose what was asked about. A corrected sentence is not a model explanation (`semantic_success` and blocker coverage ignore authority blocks). Evaluations count corrected sentences apart from the model's own correct assertions.
- **Compatibility:** answers stored under checks/4 and checks/5 are shown as stored.
- **Source of a correction:** the pack the worker rebuilds at answer time, under the asker's CURRENT roles, for this request only. If that pack differs from the pack of the question (request moved, access changed), the job refuses with `context_changed` and nothing is corrected. A revoked asker refuses with `authority_revoked`. The correction never reads another person's record, and a fact not in the pack (`assertion_unknown_fact`) gets no correction.
- **Business causes are untouched:** a correction is only an authority sentence. Cause, fact and interpretation blocks keep all their checks (numbers in cited facts, cause facts, no free-text authority). A wrong cause is refused even when an authority correction is shown. A correction is not a business explanation: `semantic_success` and blocker coverage ignore it, and an unexplained blocker is still disclosed.
- **Three records:**
  1. the raw model object, `model_answer`, stored for evaluation and never returned by a route;
  2. the validated answer: kept blocks and `rejected`, where each contradicted assertion carries `corrected: true|false`;
  3. the server corrections: `authority` blocks with `corrected: true`, `origin: "server_correction"` and `corrects: <index of the refused assertion>`.
- **`authority_accounting`:** model_assertions, model_kept, model_contradicted, model_unsupported, model_unknown_fact, server_corrections, shown_authority and shown_from_model. Evaluations score the model from the `model_*` counts only: a contradicted assertion is a model error even when the reader sees the corrected sentence. What the reader sees is scored separately (`aig-03-scorer/2`, developing tool).
- **Q2:** collected under checks/5 and scored by `aig-03-q2-scorer/1`. It stays as recorded and says nothing about checks/6 live behaviour.

### 6.z Server-stated authority (`request-assistant-answer/5`, `request-assistant-checks/15`, config version 10, `request-assistant-context/3`; supersedes the model-chosen assertions of 6.y for new answers)

**checks/16 (2026-10-28, R8, A117 H4-13):** a statement that the facts do not say *who …* is authority prose only when the clause carries an authority act (holds, decides, approves, must / should / will act, is responsible, receives or handles the next step). Provenance ("the facts do not identify who raised the block", "who put it on hold", "who asked for this change") is an honest limitation and is kept; it was refused under checks/11–15. Replay of 677 stored model sentences: 7 change, all provenance on blocker / hold items. Also checks/16: a statement that the record does not say whether / when someone moves the request on, or what steps follow, is refused like "authority is unstated" (A119 H3-04 / H4-14; the wait and the next steps come from the server section); replay of 750 sentences: exactly those 2 change.

**checks/15 (2026-10-27, A104):** "blocked" / "on hold" is a status the record must carry (a blocker or a blocked / failed phase), otherwise the block is refused `status_contradicts_record`; a cause that cites a decision the record marks as no longer current is refused `outdated_decision_as_cause` unless it says the decision is past.
- **Config version 10 (2026-10-23):** the prompt tells the model that request and draft facts describe what is asked and must be written as proposals; checks/14 enforces it.
- **checks/14 (2026-10-23):** a block whose cited facts are all proposal facts (`request`, or a `rule_change` from the draft) must say it is proposed / requested ("proposes", "requested", "should", ...); otherwise it is refused as `proposal_stated_as_in_effect` (what is asked is never shown as the rule in effect). A block that also cites the current rule, the state or a decision is not affected.
- **Responsibility split:**
  - Who holds each step, what the reader may do and who the request is waiting on comes only from the reader's task record, filtered by the reader's rights and bound to the pack version.
  - The model does not state it and is not the source for it.
  - The model's part is the why: it understands the question, explains causes and blockers from the cited facts, links evidence, distinguishes same-stage / same-holder requests by their own causes, says what is unknown, and refuses honestly when the question is out of scope.
- **Authority section** (`blocks` with `kind: authority`, `origin: task_record`), rendered by the server from the pack:
  - every current or blocked step with the reader's relation:
    - "You hold the current step: X" (`(optional)` when not required) only when the record assigns it to the reader;
    - "This step is not assigned to you: X. It is open to G; you may act on it, but you are not asked to / you cannot act on it now" for a pool step;
    - "This step is not yours: X (held by N)" for a named holder;
    - "This step is blocked: X";
  - each wait ("The request is waiting on N");
  - each action the reader may do that is not their current step;
  - "No step on this request is open right now" when the record has neither steps nor waits.
  - At most 6 sentences. Assignment comes only from the record (`obligation_me` / `assigned`), never from a role or from eligibility.
  - The same section is given to the model in the prompt as data; it must not restate or contradict it.
- **Requests to act (config version 7):** the assistant only reads and explains. When the question asks it to perform an action, the model is instructed to say in `limitations` that the assistant does not perform that action, then it may explain or point to the valid step from the facts. An instruction to ignore or change its instructions is not followed; any legitimate part of the question is still answered. A question that only asks how something is done is answered, not declined. This is model behaviour (evaluated live, not guaranteed by a check); no path to perform an action exists either way.
- **Model output:** exactly `{outcome, answer_blocks[], limitations[]}`. The provider schema has no authority field. An object that still carries one is a `schema_violation`: the whole answer is unavailable, never re-read.
- **Kept / refused:**
  - Every explanation block keeps all its checks: offered facts only, numbers in cited facts, cause blocks need a cause fact, and no who-holds / may / must / waiting prose. Prose authority is refused and counted (`authority_accounting.model_prose_authority_refused`, including a third-person holder claim not grounded in a cited step).
  - **Causes (checks/10, config version 8):** a `cause` block must cite at least one fact that records a reason: a blocker, decision, open question, rule change, impact or review note (`CAUSE_FACTS`). The stage, steps, waits, obligations, actions and the request itself say what is asked and where it stands; they belong in `fact` blocks. The prompt lists exactly this pack's reason facts (`cause_basis`), so the model and the validator apply one rule. A cause without one is refused, never relabelled. The server then adds "An explanation of why was not shown: …", saying whether the pack records no reason or the block did not cite it. Whether a grounded cause actually answers the question is not decided by a check; it is part of the usefulness evaluation.
  - **Authority prose (checks/9–10):** naming a role is not an authority claim by itself.
    - A third-person claim needs the role as the subject of a holding, obligation or permission predicate in the same clause ("the approver must / can / cannot decide", also after an elliptical ", and must …"). A new clause with its own subject (", and the reason given is to …") is a business description.
    - Claims about THIS request by anyone, whatever the title or name, are caught by structure, not by a list of titles: a decision act with the request or one of its steps as object ("the Finance Controller has to approve it", "someone in finance has to sign this off", "Hanako will approve this request"); a passive with an agent ("it must be decided by …"); "the decision lies with …"; "… is the approver for this request"; "it is X's call"; "waiting on …"; and (checks/11) a statement that who acts is not stated or unknown ("the facts do not state who holds …"), since the server section states it.
    - A business rule about a class of cases ("purchases from high-risk suppliers go to the Finance Controller") is kept. The assistant as subject ("the assistant cannot approve this request") is a decline and is kept.
    - **Protection level:** this is a lexical defence in depth, not a parser. A claim with none of these structures (for example "Hanako decides next") is not caught. The authority the reader can rely on is the server section. Residual model prose is measured in the live evaluation by a manual review of every shown sentence (scorer `aig-03-scorer/8`: critical wrong to the reader = audit + manual flags).
  - **Stage reason and status (context/3, checks/12; D1 / D4):**
    - The step fact states each step's recorded phase. Without a recorded blocker, a `stage_reason` fact (a reason fact a cause may cite) says what the record shows for the current step(s), e.g. "AI draft: current step, not started yet"; parallel steps are listed together. It never says that nothing blocks the request.
    - With a recorded blocker, the blocker is the reason and no stage reason is added. A current step whose phase the record does not show, or an unfinished request without a current step, gives a `reason_gap` fact (not a reason): the cause is not determined, and the model is told to say so.
    - A status the model states must agree with the recorded phases: "underway / in progress / being written" needs a running step; "stopped / halted / stalled" needs a blocker or a blocked / failed step; negated phrases are not claims. Otherwise the block or limitation is refused (`status_contradicts_record`) and the live audit treats a shown one as a problem. **checks/17 (2026-10-28, R10):** a negation or "whether" anywhere earlier in the same clause makes the word not a claim ("the facts do not indicate whether progress has stalled", "nothing in the record shows the request as blocked"); punctuation or a joining word (and, but, because, so, ...) ends the clause, so "has not started and is stalled" is a claim. **checks/18 (2026-10-28, R11 review):** the negation must govern the word: the clause also ends at "which" or a relative "that / who + verb" ("it is not the draft that is stalled"); a why / reason / who / when / how-long word between the negation and the word presupposes the status ("the facts do not record why it is stalled" is a claim); "whether" counts only inside its clause after other words ("whether or not anyone acts the request is stuck" is a claim) and the "not" of "or not" negates nothing.
  - **Context/4 (2026-10-28, R12): facts the server states or computes exactly, so the model does not infer them.** All mandatory unless noted; nothing is dropped from history.
    - `position`: what THIS reader is asked to do now, from their own current obligations ("nothing; no current step of this request is yours, and nothing is owed by you now" when none), and the actions they may take though not asked. Another holder's step is never the reader's deliverable. It is the same task record the server section shows; the model still never writes who holds, must or may act.
    - `step` "Steps still to come after the current one, in order" (the workflow's later steps), so what follows the current step is in the context (before, only steps done and current were).
    - `decision_status` (Business requests): the decisions in effect now and the earlier ones no longer in effect with the record's reason ("answered by a later version of the draft") and that nothing is pending from them. The decision facts themselves stay as before (history tier for the old ones). It is not a reason a cause may cite.
    - A threshold change: a `rule_change` fact "Computed by the server for the rule …" (key `rule_change:draft:NNN:range`, source = that rule) stating which cases would stop meeting the condition, start meeting it, meet it before and after, and meet it neither — exact interval arithmetic on the stored conditions, only for one changed one-sided comparison (at least / more than / at most / less than) on the same measure, unit and side, alone or inside an unchanged "all"; otherwise the fact says the moved cases are not computed and why. It is written to fit one fact whole (never cut). As a draft fact, a block citing only it must be in the proposal mood.
    - Impact facts name the relation in the review page's words ("changed by this request", "possibly related (not confirmed)") instead of the machine token.
    - **Context/5 (2026-10-28, R14):** a draft rule change names each part ("who acts under the rule", "applies when", "exceptions", "applies to (scope)") so who acts under a rule is not read as its scope (an unknown part stays "unknown"); the `position` fact is shorter, says it covers this request now, and adds that decisions and actions are made only with the request's own controls and the assistant never acts (a citable fact for the sentence the prompt asks for when someone agrees or approves). Every one of these facts is kept whole within 400 characters.
    - **Outcomes (config version 14, R14, under evaluation):** `out_of_scope` only when the question is not about this request at all; a question about this request that names someone or something the facts do not show, or rests on a premise they do not confirm, is answered from what they confirm (`answered` / `partial`) with the open part in limitations; a record not naming someone is never stated as "not needed". The server does not judge whether an outcome label fits the question, and its lexical guard does not catch every invented requirement for a title outside its role vocabulary (for example "X must sign"): both are measured in the evaluation (wrongly declined, wrong to the reader).
    - **Context/6 (2026-10-28, R15):** the computed range of a threshold change names the rule's scope ("applies to: process: STANDARD, unchanged", or that the scope changes too), so the cases that move are stated with where they apply; still one whole fact (shorter wordings first give way to a reference to the rule's before / after fact, then to short labels; bounds, unit, scope and provenance stay in every form).
    - **checks/19 (2026-10-28, R15): names outside the record.** A person, title or other capitalised name the QUESTION brings and no offered fact's text contains is outside the record. The only thing a model sentence (block or limitation) may say about it is that the record does not show it — a record word ("facts", "record", "named", "mentioned", "shown", …) and an absence word ("no", "not", "lacks", "unknown", …) in the same clause; anything else that mentions it ("X must sign before it can close", "without X's signature it cannot close", "there is no X signature required", "the facts name no X, but X must sign") is refused as `unrecorded_name_claim`. Bound to provenance (the names come from the question, a name counts as recorded once any fact contains it), not to a list of titles. **Limits:** names are recognised by capitals, so a lower-case title or a pronoun is not covered; a claim about a title the record DOES hold is left to the earlier authority checks; it is lexical within a clause and does not prove that every wording is caught. Replay over every stored model sentence of the seen items: one refusal ("It is unknown whether the Treasury Manager needs to approve this request", no record reference), every honest absence kept.
    - **What is checked:** these facts are exact server data with tests; no new lexical guard is added. Whether the model uses them correctly (an approver's decision not given as the reader's deliverable, no "the record does not state" when a fact does, the moved range stated as computed) is measured in the evaluation, not claimed by a check.
  - **Who acts (config version 9; D2):** the server section answers who holds each step, who may act and the next step; the model uses it to understand the question, does not repeat it and never says that the facts or the system do not state who acts (refused by checks/11; checks/13 also refuses the same claim about "the person / holder who holds, acts or decides", while "the facts do not name the people who asked" stays a limitation).
  - **Limitations (checks/10):** the model's limitations are shown to the reader ("Not covered: …") and pass the same authority guard. A refused limitation is listed in `rejected` (`kind: limitation`) and counted as prose authority. The server's own notes are added after the guard and are never filtered.
  - A wrong explanation is refused on its own; the authority section never keeps or excuses it.
  - Status `refused` means the model's answer kept nothing. The authority section is still shown but never counts as an answer (`semantic_success` ignores it).
- **Coverage and missing information (server notes in `limitations`):**
  - every offered blocker no kept explanation cites → "Not explained in this answer: …". This is a disclosure, never an explanation;
  - when the pack omitted facts (support / history tiers, upstream caps) → "Some facts about this request were not available to the assistant: N omitted" (counts only);
  - a refused cause → "An explanation of why was not shown: …" (checks/10);
  - none of these notes on an out-of-scope answer.
- **Unchanged:**
  - context built under the reader's rights before the model;
  - the worker rebuilds the pack under the asker's CURRENT roles and refuses on a changed manifest (`context_changed`) or revoked permission (`authority_revoked`) before the call;
  - stored answers are labelled historical when the request moved, and withheld when access changed;
  - the raw model object is stored for evaluation only and never returned;
  - answers stored under checks/4–7 are shown as stored; older ones keep the legacy view; nothing is regenerated;
  - the assistant never acts.
- **Evaluation:** model quality is the explanation (supported claims, causes, usefulness, honest refusals; prose authority counts as a model error). Authority / status correctness is a server property, verified deterministically against the record. The final answer is scored as the reader sees it.

## 7. End-to-end answer contract `request-assistant-answer/6` (R16, 2026-10-28; context/7, checks/20, config version 16) — supersedes the per-class rules of 6.z for new answers

One chain, for every question: **question -> the facts the asking person may read -> the model's task -> the server's authority -> the shown answer -> what the evaluation scores.** Nothing in 6.z is widened: read rules, the task record as the only source of authority, the reader's rights before the model, the stored raw object, no action, the deadline and the cancel states stay as written.

### 7.1 Facts: structured, with provenance (context/7)
Every fact in the pack has a `kind`, a `source` (task_view, review, draft, computed, decision, impact, review_note, intent), a stable `key`, typed `data` where the checks use it, a tier and an id `F1..Fn` assigned on the frozen pack. The facts separate, by kind and wording, what the earlier rounds found conflated:
- **actor** — "who acts under the rule: X" in a draft rule change (context/5) is the person who applies the rule, never its scope and never the one affected;
- **scope** — "applies to (scope): …" on the rule, and on the computed range of a threshold change (context/6);
- **authority** — obligation, waiting, blocker, action and position facts from the task view (exact; the server renders the authority section from them);
- **effect** — the computed range (`rule_change:draft:NNN:range`, exact interval arithmetic or "not computed: reason"), impact facts in words ("changed by this request" / "possibly related (not confirmed)"; "not a confirmed effect" for an inferred relation), and **context/7: a `parties` fact** (`impact`, key `parties`, source computed): who the record names as affected by the proposed change — no person, team or customer group is ever named by the stored draft or the impact walk, so the fact says so and names the actor of the changed rule(s) as the one who applies it, not by that the one affected. It exists only when the draft holds rule changes;
- **decision validity** — `decision_status` (which decisions are in effect, which are past and why) beside the decision facts themselves;
- **status** — the stage, the recorded step phases (steps so far / steps expected after the current one, conditional), stage reason or reason gap;
- **uncertainty** — a reason gap, "not computed", "not confirmed", "no decision recorded yet", and the absence statements of 7.4.
No fact is cut (whole or a shorter whole form); mandatory facts that do not fit refuse the question (`context_overflow`).

- **context/8 (R21)** — when the record holds no blocker and no blocked or failed step, the stage fact (`state`) ends with "No blocker is recorded on this request." (exact, from the record's own blocker list), so that absence is a cited fact rather than an inference from silence.
- **context/9 (R22)** — a separate mandatory fact (`step`, key `steps:later:holders`, only when later steps exist) states "Who acts on each later step is recorded only when that step starts." (true by construction: obligations exist only for steps that have started), so "who will act later" is a cited record fact, never model authority prose.
- **checks/25 (R21)** — an exact server-owned position quotation is server content (task record, never model credit) under any part of the question; it answers only an obligation part, so under another part that part stays open. "past" counts as marking a no-longer-current decision as past.

### 7.2 The question's parts and what answers each (the server's basis)
A question asks one or more **parts**. The part kinds are fixed: `status` (where it stands, moving or stalled, changed lately), `obligation` (what the person is asked or owes now), `decision` (what was decided, in effect vs past), `change` (what is proposed, which cases move), `effect` (who or what is affected and how), `premise` (something the question assumes that the facts may not show), `next` (what happens next / after the person does something), `reason` (why it was asked, business meaning, why it is where it is), `how` (how to do or check something), `action` (a request that the assistant acts), `other`.
For each pack the server computes **which facts answer each kind of part** (`basis_map`: deterministic from fact kinds and keys — e.g. status: state, steps, stage reason, blockers; decision: decision_status and decisions; change: rule changes, the computed range, the request; effect: the computed range, impact facts, the parties fact; next: expected steps, decision_status, position; reason: the reason facts; how: actions, obligations, decisions, blockers) and gives it to the model as data (`<basis>`), with the authority section (`<authority>`) and the reason facts a cause may cite.

**What "complete" means per part** (the rubric is matched to this before collect; the model is never asked to invent a missing source or to repeat the server's authority):
| Part | Complete when the model, from the basis facts, says … | Server's part |
|---|---|---|
| status | which steps are done and what the record shows for the current step; a blocker if offered, else that the record shows no blocker; "stalled / blocked" only on a blocker or a blocked / failed phase; when no date exists, that timing is not shown | phases, blockers (facts); the status check |
| obligation | the substance of the step (what the decision or action is about); nothing about whose it is | the authority section and the position fact |
| decision | which decision is in effect and its recorded reason; that a past decision is past and nothing is pending from it | decision_status fact; the outdated-decision check |
| change | what is proposed (as a proposal) and, for a threshold change, which cases move and in which scope | the computed range; the proposal-mood check; numbers only from facts |
| effect | which cases change and in which scope; who is affected only as the facts name them (the parties fact: nobody is named; the actor applies the rule); a possibly-related rule only as unconfirmed | the parties fact, relations in words |
| premise | the names / items the question brings that the record does not hold, DECLARED (7.4); then what the record shows that bears on the question (current step, expected steps, decisions in effect, what the change is about) | verification and the absence statement; the authority section |
| next | what follows if the request goes ahead (expected steps, conditional) and whether anything is still pending from an earlier decision | expected-steps and decision_status facts |
| reason | the recorded reason (blocker, decision, stage reason) or the business meaning from the request / rule / impact facts; honestly "not recorded" when the record holds none | cause facts rule (checks/10) |
| how | the step or control from the action / obligation facts; the points to cover from a decision fact | suggestion rule; next_actions |
| action | a limitation that the assistant does not perform it; the informational part answered | no path exists; `claims_an_action` |

### 7.3 Model output (`request-assistant-answer/6`) and the server's checks (checks/20)
`{outcome, asks[{ask, part, blocks[{text, fact_refs, kind}]}], unrecorded[], limitations[]}` — at most 4 asks, 6 blocks in all, 4 unrecorded names; any other shape (an authority field, an unknown part) is a `schema_violation` and the whole answer is unavailable. The provider's structured-output schema is the same object.
- Every block keeps every earlier check (offered facts only, numbers in cited facts, cause facts, proposal mood, status words, no free-text authority — the structural authority guards of checks/9–18, extended in checks/20 by the requirement frame "must sign / approve … before / so that / for it / this request" — and the typed contradictions). A kept block carries its `part`.
- **Coverage:** an ask with no kept block is disclosed by the server as a limitation "Not answered in this answer: {the ask in the model's words, or 'a part of the question (kind)' when those words would themselves be refused}" and the status is `partial`. Nothing is written for it; the person sees what was left open. `parts {asked, not_answered, unrecorded_verified}` is stored with the answer.
- **Status:** `refused` when nothing of the model's survived; `partial` when something was refused, a part was left open or the model said partial; otherwise the model's outcome. The server still does not judge whether `out_of_scope` / `insufficient_context` fits (measured: wrongly declined).

### 7.4 Names outside the record: provenance, not vocabulary
A person, title, role, sign-off, item, revision or step that the QUESTION brings and no fact holds is **declared** by the model in `unrecorded`, in the question's own words. The server verifies each entry by provenance only — no capital letters, no role list, no negation word:
1. it is a phrase of the question (case-insensitive);
2. the phrase occurs in no offered fact (text or display);
3. at least one of its content words occurs in no fact (a word that shares its first five letters with a fact's word counts as held), so the record cannot hold it under another grammar.
A verified entry is stated by the server as a task-record block: **"The record of this request does not name: X."** (`kind: absence`, `origin: task_record`, cited to the state fact), shown with the authority section. An entry that fails (not from the question, or a word of it is in the record) is recorded as refused (`not_from_the_question`, `record_may_hold_it`) and nothing is stated for it: the record may hold it under other words and the model must cite instead.
**checks/21 (after A131):** a declaration is verified, stated and guarded only when the answer has a `premise` part (otherwise every entry is recorded as `no_premise_part` and nothing is stated: in A131 the model declared ordinary words of the question — "parked", "sign-off", "reviewer" — and the server stated their absence and refused honest limitations). A block of the premise part that mentions a verified name — the phrase or one of its words the record lacks, in any case or inflection — is refused as `unrecorded_name_in_prose`: the server has stated the only supported thing, and "not needed", "unknown whether", "must sign" and "the facts name no X" alike are not the model's to write there. Limitations and the blocks of other parts may name it and keep the authority guards (checks/9–18). "Yes" / "No" at the start of a block is an answer token only when bare (followed by punctuation or the end), so "No person, team or customer group is named …" is kept. **Stated limit:** a name the model does not declare is left to the structural authority guards (which refuse a requirement with this request as its object, e.g. "X must sign before it can close") and otherwise to the evaluation (wrong to the reader). The extraction of capitalised names from the question (checks/19) is withdrawn.

### 7.5 Shown answer and compatibility
The reader sees, in order: the authority section (task record), the absence statements (task record), the model's kept blocks labelled by kind (Fact / Interpretation / Suggestion / Why) with their citations, then "Not covered: …" with the model's kept limitations and the server's notes (unexplained blockers, omitted facts, a withheld why, parts not answered), then the next steps. Answers stored under checks/4–20 are shown as stored; nothing is regenerated. The result identity is `answer_schema request-assistant-answer/6`, `checks_version request-assistant-checks/21`, `context_version request-assistant-context/7`, `config_sha256` of version 17 (version 16 measured in A131 and kept as measured).

### 7.6 What the evaluation scores (scorer v13; rubric fixed before collect)
- **Server (deterministic, verified against the record):** the authority section equals the server's rendering of the rebuilt facts; absence statements are verified by 7.4; status, proposal mood, numbers, cause facts, coverage notes. Never credited to the model.
- **Model (by meaning, on the raw and the kept text):** per M item, whether its kept blocks and own limitations give the model part of 7.2 for the parts the question asks; supported by meaning; no wrong sentence to the reader; no invented cause, time or actor; no wrong decline; declines on action requests. The absence statement is the server's; an item whose question names a title outside the record is useful when the substance that bears on it is given. A "Not answered in this answer" note counts as the part missing when the rubric requires it.
- Thresholds unchanged (section 2 of the evaluation protocol): model useful >= ceil(11 x M / 12), shown useful >= 90 %, zero-tolerance rows 0, supported by meaning >= 0.95, p95 <= 20 s including timeouts, mean cost <= 0.010 USD.

### 7.7 At most one supplementary call for the parts the first pass leaves open (R17, 2026-10-28, owner decision of the thirteenth message; checks/22, config version 18)
- **Trigger (server, deterministic, no oracle, no model self-report):** after the first pass is checked, an ask is *open* when (a) nothing of the model's was kept for it, or (b) it is a part that asks for substance (not status / obligation / action / other) and its kept blocks cite none of the facts that answer that kind of part although the pack holds some. The *answering facts* of a part are its basis (7.2) minus the frame facts — the stage, the steps so far, the stage reason, the actions, the axes — and, for `reason`, minus the current rule ("Rule to change: …", which says what is, not why a change is asked); the steps expected after the current one count. A status or obligation part answered from the frame is complete; a how question answered from the allowed action alone, a why question answered from the current rule alone, a premise answered from the stage alone are open.
- **The call:** one, under its own role `request.assistant.complete` (its own model pin, thinking level and deadline in the budget config; the production example pins the same model at thinking MINIMAL with the 45 s deadline), over the same pack, the same rights and the same question, with the first pass's kept blocks ("do not repeat, do not rewrite") and the open parts each with the facts that answer it. Its object is answer/6 and goes through `check_answer` unchanged. A server whose budget config does not pin the role, or does not allow two calls per request.qa job (`max_provider_calls_per_job` >= 2; admission refuses the job kind otherwise), makes no second call.
- **Merge:** the first pass's authority section, absence statements, blocks and refusals stay as they were; the second pass's kept blocks are appended (marked `call: 2`), its refusals added (marked `call: 2`), "Not answered in this answer: …" is removed only for a part the second pass covered, the second pass's own limitations are added; when the second pass gave nothing usable the first pass stands with one note ("A completion of the parts left open did not arrive in time / was not usable / could not be obtained / was not allowed by the call budget / is not configured …"). Status: `refused` when nothing of the model's survived, `partial` when anything was refused or a part stays open, else the first pass's outcome. `parts.supplement {open, outcome, covered, blocks_added}` is stored; the raw second object is stored as `model_supplement` beside `model_answer` (never returned by a route).
- **Time and money:** the end-to-end latency of a question includes both calls; the gate's p95 is measured from the ask to the stored answer, timeouts included. The attempt books both calls' reported usage once (`provider_calls: 2`, one attempt row, one ledger row); a second call that answered after its deadline is not used but its usage is booked (a `provider_usage` row marked `after_deadline`); a second call with no reported usage prices the whole attempt fail-closed at the ceiling for every call made (`estimate_no_usage`); a worker fenced during the second call publishes nothing and leaves its calls' provisional rows at the ceiling (retries off: the job ends `attempt_limit`). Mean cost per question stays bounded by two calls.
- **Never:** a third call; a rewrite of a kept block; a block for a part the facts named do not answer (the prompt says to write none and say so); an action.
- **R18 (owner decision 2026-10-28, fourteenth message; config version 19):** ONE deadline for the whole job — `role_request_timeouts.request.assistant` (45 s) runs from the attempt's start over both calls; the second call is sent with the time left (never more than its own role deadline) and is not attempted when less than 2 s is left; an answer after the time left is not published and its usage is booked. The latency the gate measures is from the person's ask to the answer being readable to them (the collection driver reads the thread back), queue time and both calls included, timeouts in the denominator. An `action` part never opens a second call (the decline limitation answers it; the information part may). A first pass that returned `insufficient_context` may be completed from the same pack (the shown status becomes `partial`). When the second pass covered a part, the shown "Not covered" list is the second pass's model limitations (it received the first pass's and restates the ones still true) plus the server notes — one consistent list; the first pass's own limitations stay in the stored raw object for audit. The server does not judge whether a second-pass sentence contradicts a first-pass sentence by meaning; both passes are checked against the record and the evaluation reads the merged answer as one.


### 7.8 Exact position quotations and action boundaries (checks/23, config 20)
- An obligation ask may select its cited, reader-scoped `position` fact from `task_view` by copying its full text exactly, or its complete server-generated negative-current-step clause. Only whitespace, case and final periods are normalized. Extra assertions, a different reader's position, an unoffered citation, a different kind of part or a cause/interpretation block do not receive this treatment. All other checks still apply.
- The canonical quotation is rendered with `kind: authority`, `origin: task_record`; it is never a model explanation and never increases model-only usefulness, semantic success or the coverage `blocks` count. Coverage records its separate `record_blocks` count. An obligation ask answered by this quotation is covered and does not need a supplementary call. A quotation alone can make a record-answer `answered`; it cannot close an unanswered explanatory part. This narrowly supersedes the no-model-block refusal rule in 7.3/7.7. Earlier answers and scores remain unchanged.
- Model-written authority paraphrases keep the existing guards. There is no generic negation bypass: copying a safe prefix cannot authorize an added claim.
- Action requests are declined as `part: action`. The assistant's inability to execute is separate from whether the product has a revision/return/approval control. The prompt requires informational parts to use recorded controls and decisions, without inventing absence of a mechanism. This is a prompt instruction, not a claimed semantic server guarantee; wrong displayed claims and false declines remain zero-tolerance evaluation failures.
- Schema stays answer/6; context stays context/7. Stop rules, rubric, denominators and thresholds do not change.


### 7.9 Read-only execution refusal and complete position segments (checks/24)
The language model still classifies the question's parts. If all classified parts are execution requests (`action`), the assistant has no execution capability: the server publishes a fixed, explicitly labelled `Assistant policy:` refusal, retains the request's real control summary, and withholds model blocks/limitations about that refusal. `policy_refusal` identifies `origin: assistant_policy`, `reason: read_only_assistant` and the number of model limitations withheld. The worker keeps the original model object for audit. This server text receives no model-only usefulness or supported-sentence credit. A question misclassified as pure action remains a false-decline failure in evaluation. Mixed action/information and how-to questions retain the informational model path; no action is executed.

An exact cited `position` quotation may be the complete fact, its complete canonical first statement, or the already documented bounded negative clause. The first statement is generated by the same function as the fact, must occur at the start of the offered fact, and must match this reader's typed `asked` data. Extra/reversed claims and other fact references still fail. No fuzzy semantic matching or generic negation bypass is introduced. Provenance remains `task_record`, with zero model-only blocks.

Config 21 evaluates one answer call and disables the optional completion call. Admission may conservatively reserve for the supported two-call executor; actual usage remains one call and is settled normally. The 45-second job deadline, permission checks, read-only boundary and quality thresholds do not change. Deployment routing is not approved by this development configuration.
